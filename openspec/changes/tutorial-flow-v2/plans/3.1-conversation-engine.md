# Conversation Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> (inline) to implement this plan task-by-task. Steps use checkbox (`- [ ]`)
> syntax for tracking.

**Goal:** A headless engine walks a tutorial definition beat by beat, saves
the learner's progress in the workspace so project sync carries it, restores
it on reload with runs interrupted and never repeated, and emits
`tutorial_started` and `tutorial_finished`. Every card ticket (3.3 to 3.6) and
every run ticket (4.1 to 4.3) renders or feeds this engine's state.

**Architecture:** A new feature slice, `features/tutorial-conversation`, with
no React in `model/`. A pure reducer over the definition and the saved
progress produces the next progress and a queue of effects. A store,
`PgConversation`, is the one entry point: it loads the save for the open
workspace, dispatches, drains the queue through two ports (the workspace's
files and the runner), persists, and notifies. The feed's turns are a fold
over definition and progress, computed by `view`, so the save holds facts and
never copy. Two ports keep the engine headless: `Workspace` (read and write a
file, like the assistant's `PlaygroundBridge`) and `Runner` (build, deploy,
run, call, reporting stages and a result). The engine ships with in-memory
implementations for tests; the run tickets replace the runner's.

**Tech Stack:** TypeScript, vitest in-source blocks, `PgTutorial.getStorage`
for the save, `createTracker` for events.

**Spec:** `openspec/changes/tutorial-flow-v2/specs/tutorial-conversation/spec.md`,
"The lesson and the assistant share one thread" (progress, reload, Start over)
and "The conversation is measured" (`tutorial_started`, `tutorial_finished`);
`tutorial-runs/spec.md`, "A reload interrupts a run, never repeats it". Design
D2 and D3.

## Sources, and where they differ

The prototype (`almaz/mobile-tutorial-prototype`,
`design-system/src/prototype/tutorial-v2/store.tsx`, `check.ts`,
`landing.ts`, SPEC.md "State" and D28 to D30) is the model for the reducer's
actions, `flow()`, the write queue and `insertBlock`. The engine differs
where the app's shape forces it:

- **Files are not in the state.** The prototype's reducer holds `s.files`;
  here `PgExplorer` owns the files. The reducer reads a file's content only
  through the actions that carry it (`edit`, `written`) and writes only
  through the queue. The pure `insertBlock` is ported as is.
- **The thread is derived, not stored.** The prototype persists `thread:
  Turn[]`, copy included. The spec says the save holds facts, never copy, so
  `view(definition, progress)` rebuilds the turns from the definition on
  every read, and a fixed typo shows on reload.
- **Reload renders whole.** D28 types out only turns later than the page
  load; the spec says a reload renders turns whole with no typing or rise.
  Both agree in effect: a turn whose `at` is before the load has no
  animation. The engine marks it; the feed (3.3) obeys it.
- **Interrupted runs.** The prototype turns `running` acts into
  `interrupted` on load (SPEC "Persistence"). Kept, and the start time is
  saved so 4.2 can recognise a deploy that confirmed before the reload.

Decided here, no source settles it:

- **Who writes a block.** The engine, through the `Workspace` port, from its
  queue. The question card (3.5), Skip, "Show me the fix" and the typed-key
  fill all dispatch an action and never touch a file. `written` is dispatched
  only after the write lands, with the lines it took, so the save never
  claims a write that failed.
- **Who judges a goal.** A `Judge` port, `(goal, result) => boolean`. The
  engine's stub passes any `ok` result; task 3.2 supplies the real checks and
  replaces the stub where the store is wired.
- **Events.** The spec names `tutorial_started` and `tutorial_finished`, and
  the `tutorial` prefix belongs to `entities/tutorial`, so the two events are
  declared on that slice's tracker. The feature's own `model/telemetry.ts`
  exists, as `slice-structure.test.ts` requires, and re-exports it with the
  reason.

## Global Constraints

- The slice imports only `@/entities/tutorial` and `@/shared`, plus the legacy
  roots (`utils`) in `store.ts` alone. Nothing imports `views/flow/lessons`,
  which task 7.1 deletes.
- Every reducer action carries `at`; the reducer never reads the clock,
  the file system or a global.
- The save is `.workspace/tutorial-storage.json` key `conversation`, through
  `PgTutorial.getStorage`, written with `writeWorkspaceFile` as that storage
  does. Its shape extends `ConversationSave` from
  `entities/tutorial/model/progress.ts` (`version: 1`, `passed`,
  `finishedAt`) without changing those three fields.
- A save whose `version` is not 1, or that fails `parse`, and a file that
  exists but could not be read, set `loadFailed`: the tutorial opens on the
  intro, the failure is logged and reported, and the store refuses every
  write for that load, as `PgLesson` guards it, so a real save is never
  replaced by a fresh one.
- On load, a run saved as `started` becomes `interrupted`; nothing resumes.
- Start over writes a fresh save; the assistant's thread is untouched.
- No file write except through the `Workspace` port, and none for a `say`
  beat.
- Conventional Commits, scope `client-v2`, ticket `HOO-2350` in the subject.

## Decisions this plan takes

- **Save shape** (`model/progress.ts`):

  ```ts
  interface ConversationProgress extends ConversationSave {
    version: 1;
    passed: string[];
    finishedAt: number | null;
    startedAt: number | null;
    /** Where the lesson stands: before Start, in a step, or finished */
    cursor:
      | { kind: "intro" }
      | { kind: "step"; stepId: string; beat: number; fail: boolean }
      | { kind: "finished" };
    /** Every resolved beat, by id; copy is re-derived from the definition */
    beats: Record<string, Resolution>;
    /** Every act's run, by beat id */
    runs: Record<string, RunRecord>;
    /** When each step started and passed, for the divider's time */
    times: Record<string, { from: number; to: number | null }>;
  }
  ```

  `Resolution` is `{ kind: "said"; at }`, `{ kind: "written"; at; file;
  lines }`, `{ kind: "picked"; at; option; attempts; wrong: number[] }`,
  `{ kind: "typed"; at }`, `{ kind: "skipped"; at; via: "button" |
  "call_panel" }`, with `hinted?: true` on a question. `RunRecord` is
  `{ status: "started"; at }`, `{ status: "ok"; at; took; result }`,
  `{ status: "failed"; at; took; result }` or `{ status: "interrupted"; at }`.
  `result` is the facts a run ticket defines (`RunResult`, a discriminated
  union by act with signatures, program id, logs, times, the parsed error);
  3.1 ships it with the fields the spec's cards read and the run tickets add
  to it.

- **Actions** (`model/reducer.ts`): `start`, `pick`, `hint`, `skip`,
  `typeIt`, `edit` (file and its content), `written`, `act` (an act beat
  pressed, or its composer word), `stage`, `ended`, `passed` (a goal met
  from the Call panel or a client run), `explain`, `fixMyself`, `next`,
  `finish`, `startOver`. `load` is the store's, not an action: it parses
  the save. "Show me the fix" after an unplanned failure is task 4.1's,
  with the assistant's answer it follows. There is no `tick` action: a
  turn's `at` is data, and the view shows it once its time has come. `pick` on a wrong option
  records it and posts nothing. `ended` with `ok` asks the `Judge`; a pass
  records the step and posts the win, a failed build on the step's first
  build with `onFail` moves the cursor into the planned failure, as the
  prototype's rule says. `next` after the last step posts the finish (the
  finish card shows 400 ms after the win, which `view` exposes as the finish
  turn's `at`).

- **The queue.** The reducer returns `{ progress, effects }`, `effects` being
  `{ kind: "write"; beatId; file; block }`, `{ kind: "create"; beatId;
  path }`, `{ kind: "run"; beatId; act; args }`, `{ kind: "event"; name;
  params }`, `{ kind: "focus"; file; line }`. The store drains them in order:
  a write goes through `Workspace.read` then `insertBlock` then
  `Workspace.write`, and comes back as `written`; a run goes to the `Runner`
  and comes back as `stage` and `ended`; an event goes to the tracker; a
  focus is handed to the widget's listener.

- **`view(definition, progress, loadedAt)`** (`model/view.ts`): the turns in
  order, each `{ id, kind, step, beatId?, at, live, whole }`, the live card,
  the step bar's states, the back pill's target and the composer's
  placeholder. `whole` is `at < loadedAt`. The feed never computes any of
  this itself.

- **The clock** (`model/clock.ts`): `flow()` posts consecutive `say` and
  `write` beats from the cursor up to the first `ask`, `act` or win. The
  ticket's "reading pace" is the prototype's queue cadence: `tick` posts one
  queued turn at a time, so each turn's `at` is the previous one's plus one
  constant, `TICK_MS`, with no per-word pace. The store schedules one `tick`
  per pending arrival and nothing else; a `tick` whose turn is already past
  is a no-op. Act stages are the runner's: the store forwards them as
  `stage`.

- **Ports** (`model/ports.ts`):

  ```ts
  interface Workspace {
    read(path: string): Promise<string | null>;
    write(path: string, content: string): Promise<void>;
  }
  interface Runner {
    run(act: Act, input: RunInput, onStage: (stage: string) => void):
      Promise<RunResult>;
  }
  type Judge = (goal: Goal, result: RunResult) => boolean;
  ```

  `memoryWorkspace(files)`, `stubRunner(results)` and `passingJudge` live
  beside them for tests. The real `Workspace` does what the assistant's
  `applyPatch` does (`PgExplorer.createItem` with override, then the open
  Monaco model's value), extracted into `utils/explorer/apply-file.ts` so
  neither imports the other. The real `Runner` is the run tickets'; until
  they land the store is wired with a runner that rejects with "not wired".

- **`PgConversation`** (`model/store.ts`): mirrors `PgLesson`'s shape:
  `state`, `view()`, `onDidChange`, `init()` subscribing to workspace
  switches, `_dispatch` persisting after every action but `load`, the
  `loadFailed` guard, the one save-failed toast. Public methods one per
  action. `startOver()` is the only reset.

- **`insertBlock`** (`model/landing.ts`): the prototype's `check.ts`
  function and `landingFor`'s dry run, ported with their tests, since 3.5's
  "Type it myself" and 2.2's landing line both draw it.

## Review Focus

- A reload during `flow()`: turns already past render whole, the one not yet
  arrived is dropped, not posted twice (Task 3).
- A write that fails: the queue stops, the question stays resolved as picked,
  no `written`, one `log.error`, and the next `edit` can still resolve it
  (Task 4).
- A `pick` on a resolved question, an `act` while another runs, `next` with
  no live win: the same state object back (Task 2).
- `ended` arriving after Start over or a workspace switch: dropped, since the
  run's beat id is not `started` in the current save (Task 5).
- `conversationProgressOf` keeps reading the save: `passed` and `finishedAt`
  unchanged in shape (Task 1).
