# 4.2 Deploy from the learner's wallet — implementation plan

> For agentic workers: run with superpowers:executing-plans (inline). Steps
> use checkboxes.

**Goal:** a tutorial's deploy act deploys the last build to devnet from the
learner's Playground wallet, funds the wallet itself when it is short, keeps
the program's address so a later deploy upgrades it, and reports every fact
the result card needs: cost, program id, signature, upgraded.

**Ticket:** HOO-2356. **Spec:** `specs/tutorial-runs/spec.md` "Deploy goes
from the learner's wallet on devnet", "A reload interrupts a run, never
repeats it", "Runs are measured"; design D4, D6.

## Success metric

At least 9 of 10 first deploys in the dry run land without the learner
leaving the tutorial to fund the wallet. Check: `tutorial_action_run` deploy
outcomes, 9 Nov.

## Decisions (spike, 3 Nov)

- **Uploading IDL is deferred** (Slava, 3 Nov). The build server builds
  Anchor 1.x, which dropped the legacy IDL instructions; an on-chain IDL now
  goes through the Program Metadata Program, and client-v2 has none of that
  code. Nothing in the tutorial reads the on-chain IDL. The stages are
  Writing buffer, Deploying, Confirming, with Building and Funding your
  wallet before them when they apply: three to five. Follow-up queued with
  Lead. `tutorial-runs` is updated through `/opsx:update` in this PR.
- **Funding works signed out** (Slava, 3 Nov). The editor's `airdrop`
  command requires GitHub sign-in (`checkSignedIn`); that gate is the
  browser's own, since the request goes to the public devnet RPC, which
  limits per IP. The tutorial promises a wallet with free test SOL, so its
  funding calls the RPC's airdrop directly. The editor keeps its gate.
- **The keypair is already kept.** `build` mints the program keypair when
  the workspace has none and writes `declare_id!` with it
  (`commands/build/build.ts`); it lives in `.workspace/program-info.json`,
  which sync carries and never drops (`keepLocalKeypair`). A later deploy of
  the same workspace is therefore an upgrade with no extra work.
- **The editor's deploy is not reused as a command.** It asks in the
  terminal (airdrop confirm, failed-build confirm, cancel) and reports no
  stages. The tutorial deploy reuses its parts instead:
  `BpfLoaderUpgradeable`, `additionalProgramLen`, `airdropTopUp`, and
  `sendAndConfirmTxWithRetries`, which `deploy.ts` exports unchanged. No
  editor behaviour changes.
- **Recognition after a reload** reads the program's ProgramData account:
  bytes 4..12 are the slot of its last deploy; `getBlockTime(slot)` at or
  after the interrupted run's start means that run landed.

## Split

- **This PR (model):** the deploy runner, funding, recognition, the act
  runner that composes the acts, `tutorial_action_run` for deploys, the
  spec update. Unit tests with a stubbed connection.
- **Next PR (cards, after the feed shell, HOO-2351 in #227, lands):** the
  no-wallet path, the red "Not enough devnet SOL" card, the result's meta
  line with Explorer links, the context and terminal lines, the redeploy
  nudge with the amber dot.

## Tasks

- [ ] **1. Run facts.** `RunResult`'s failed deploy gains, for
  `no_funds`, `balance` and `cost` in lamports and the wallet `address`, the
  facts of Almaz's line and the address row. Reducer and goal tests stay
  green.
- [ ] **2. Explorer URLs.** `explorerUrl({ kind: "address" | "tx", value })`
  always `?cluster=devnet` (D4: the existing helpers follow settings and the
  connection). In-source tests.
- [ ] **3. Funding.** `fundForDeploy({ connection, address, need, cap })`:
  nothing when the balance covers `need`; else one airdrop of
  `airdropTopUp(shortfall, cap)`, confirmed and the balance re-read; a
  refusal, rate limit or unchanged balance returns `no_funds` with balance
  and cost. Tests: covered, topped up, refused (429), confirmed but balance
  unchanged.
- [ ] **4. Deploy runner.** `deployRunner(deps)` for `deploy` and
  `buildDeploy`: no wallet -> `no_wallet` with nothing run; Building first
  when the program is stale (`buildDeploy`, or no build); Funding first when
  short; Writing buffer, Deploying, Confirming; cost = balance before minus
  after; `upgraded` from the program account before the run; the build's
  instruction names. Deps injected (connection, wallet, program bytes,
  loader calls, build) so the test stubs every chain call.
- [ ] **5. Act runner.** `actRunner({ build, deploy, run, call })`
  dispatches by act; an act with no runner answers `failedResult`. The frame
  passes it to `PgConversation.init`. Agreed with the HOO-2355 session.
- [ ] **6. Recognition.** `recogniseDeploy(programId, startedAt)` returns
  the landed result or null; the store asks it once per interrupted deploy
  on load and posts `ended` instead of the interrupted card. Tests: landed
  after start, before start, no program.
- [ ] **7. Telemetry.** `tutorial_action_run` declared on the tutorial
  tracker (shared with HOO-2355's build); the store emits it when a deploy
  ends with `outcome` from the result (`ok`, `failed`, `no_wallet`,
  `no_funds`) and `interrupted` on load. Failures logged without keys.
- [ ] **8. Spec.** `/opsx:update`: stages without Uploading IDL, "n of m"
  three to five, signed-out funding; task 4.2's line links this plan.
- [ ] **9. By hand on devnet:** a first deploy from an empty wallet, an
  upgrade keeping the id, a refused airdrop (rate limited) reaching
  `no_funds`.
