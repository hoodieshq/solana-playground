01Overview and topology

What it is

A browser IDE for Solana programs. The user writes Rust (or Python via Seahorse) in a Monaco editor, hits Build, and the sources are POSTed to a remote Rust service that runs cargo-build-sbf and returns compiler output plus an Anchor IDL. Deployment happens in the browser: the client fetches the compiled ELF from the server and sends the BPF loader transactions itself. A generated test panel is driven by the returned IDL. Projects live in browser storage (IndexedDB via lightning-fs), not on a server, and a built-in keypair in local storage acts as the wallet.

Runtime topology

Three processes. (1) The React client in the browser. (2) The build server, an axum HTTP service, reached over HTTPS/JSON — the only network dependency for building; the client talks to it directly from the browser and CORS is configured server-side (server/src/middlewares/cors.rs). (3) MongoDB, used only by the server for project sharing. Solana RPC is a fourth party the client talks to directly for deploy and tests. The WASM packages are not a process — they are compiled Rust linked into the browser bundle. Deploy notably does NOT go through the build server: the server only hands back bytecode (server/src/main.rs /deploy/{uuid} is a GET), and the client submits the transactions (client-v2/src/commands/deploy/deploy.ts).

03Running locally

Verified

yes

How it was verified

Executed on macOS arm64 (Darwin 25.5.0) on 2026-08-19. Client compiled in ~32s with one pre-existing warning, tsc reported "No issues found", the UI rendered with zero browser console errors, and the terminal accepted a command (solana --version reached its wallet pre-check).

Fastest path

Client only, no Docker and no Rust toolchain, pointed at the public build server. The blocker is not the server — it is that the client cannot even install until the six from-source WASM packages exist. Stubbing them takes the setup from roughly an hour to about three minutes, because all six are behind lazy dynamic imports and none are on the UI boot path.

Commands

  • nvm install 22 && nvm use 22 # package.json engines: ^22.20.0
  • npm i -g yarn@1.22.22 # yarn is not on PATH under a fresh nvm node
  • git submodule update --init # populates client-v2/public (~6.3MB of assets)
  • <create stub packages in wasm/{anchor-cli,rust-analyzer,seahorse-compile,solana-cli,spl-token-cli,sugar-cli}/pkg>
  • cd client-v2 && yarn install # ~100s
  • yarn generate-exports # REQUIRED: writes the gitignored src/*/generated.ts barrels
  • yarn generate-packages && yarn generate-tutorials # cheap, populate public/
  • BROWSER=none npx craco start # NOT yarn start - see gotchas

Public backend verified

yes

Public backend verified detail

Confirmed by direct request on 2026-08-19, not inferred. A CORS preflight (OPTIONS https://api.solpg.io/build with Origin: http://localhost:3000) returns 200 with access-control-allow-origin: http://localhost:3000, access-control-allow-methods: GET,POST and access-control-allow-headers: content-type. A real POST /build with a single deliberately broken lib.rs returned HTTP 200 in 3.5s with a populated stderr and a session uuid. Strategy A in task-01 is therefore viable: the local dev client can build against the public server with no local backend at all.

Can the client run alone?

yes

Detail

Yes. client-v2/src/settings/server/server.ts defines the server.endpoint setting with two presets — Local (http://localhost:8080) and SolPg (https://api.solpg.io) — and accepts any custom URL. Default resolution order: process.env.REACT_APP_SERVER_URL, then https://api.solpg.io in a production build, then http://localhost:8080 in development. The user can switch it at runtime from the settings gear at the bottom of the icon rail. Caveat: client-v2/src/utils/server.ts hardcodes https://api.solpg.io for the share endpoints (useDbServer) in production builds regardless of the setting.

Gotchas

  • The six from-source WASM packages block yarn install entirely. They are declared as relative file: dependencies in client-v2/package.json (e.g. "@solana-playground/solana-cli": "../wasm/solana-cli/pkg") and yarn refuses to install while the directories are absent. Building them for real is yarn setup, roughly an hour.
  • Use npx craco start, not yarn start. yarn start runs yarn generate, which includes scripts/generate-crates.mjs. That script exits early only if rustc is ABSENT; if Rust is installed it proceeds to cargo install syn-file-expand-cli and expands crate sources from the local registry. Its only product is Rust-Analyzer crate data.
  • yarn generate-exports is not optional. The src/*/generated.ts barrel files it writes are gitignored (root .gitignore, **/generated.ts) and the app does not compile without them.
  • yarn v1 COPIES file: dependencies into node_modules instead of symlinking. Editing anything under wasm/*/pkg has no effect until you re-run yarn install or copy the file across, and node_modules/.cache should be cleared since webpack does not watch node_modules.
  • Node 22 is required by engines. Node 24 was present on the test machine; Node 22 was installed via nvm to match the node:22 base image used by client/Dockerfile.
  • client-v2/public is a git submodule (github.com/solana-playground/assets). Without git submodule update --init the app has no icons, fonts, themes or tutorial content.
  • Pre-existing webpack warning, unrelated to any of the above: a case-sensitivity mismatch in client-v2/src/tutorials/ — the lazy require context looks for __template/Template while the file on disk is __template/template.ts.

State management

Pattern

Static classes, no React state containers. A module declares a plain defaultState object and a class decorated with @updatable({defaultState}) (client-v2/src/utils/decorators/). The decorator synthesises, for every property, an onDidChange<Prop> subscription method alongside a top-level onDidChange, and an update(partial) writer. @derivable adds computed values that recompute when named dependencies fire.

Write

Read

Subscribe

PgProgramInfo.onDidChange(cb) returns a Disposable

Per-module. PgProgramInfo serialises to .workspace/program-info.json inside the virtual filesystem; PgWallet uses local storage; explorer files live in IndexedDB through @isomorphic-git/lightning-fs.

Build errors

Where

client-v2/src/commands/build/build.ts

Shape returned by the server

POST /build returns { stderr: string; uuid: string | null; idl: Idl | null } (client-v2/src/utils/server.ts). stderr is the raw cargo-build-sbf output — the real compiler text.

Real example verified

Captured from a live POST /build against https://api.solpg.io on 2026-08-19 (a lib.rs containing let counter: u32 = "hello";). Verbatim stderr, showing what the assistant would actually have to work with: two unrelated "Stack offset ... exceeded max offset of 4096" errors from switchboard_solana and switchboard_v2 that are present on every build and are pure noise; then "Compiling solpg v0.1.0 (/home/solpg/programs)"; then the real diagnostic - "error[E0308]: mismatched types" pointing at "63c8e836-.../src/lib.rs:12:24" with the expected/found annotation; then the rustc --explain footer and "error: could not compile solpg due to previous error". Two things follow. The build path is prefixed with the session uuid, which is why improveOutput strips it. The leading switchboard errors are why improveOutput has an explicit /^\s*Error:\sFunction.*\n/gm removal - they are not the user's fault and must not be shown to the user or sent to a model as if they were.

Is the raw compiler output preserved?

no

Detail

This is the single most important gap for the assistant. result.stderr is referenced in exactly two places in the entire client (verified by grepping the whole of client-v2/src): once as result.stderr.includes("error: could not compile") to derive a boolean, and once as PgTerminal.println(improveOutput(result.stderr)). It is never assigned to any state module. The only trace that survives a build is PgProgramInfo.lastBuildFailed, a boolean.

What improveOutput() does

build.ts lines ~225-300. It is lossy and presentation-oriented: strips absolute paths and the home directory, removes "Compiling solpg" lines, substitutes the workspace name for the string "solpg", deletes the stack-size error and the nightly macro-backtrace note, removes the "For more information" line, injects ANSI colour, and — when the build.improveErrors setting is on — truncates to at most 3 errors and hides some it classifies as noise. Feeding this to a model instead of the raw text loses file paths and error codes.

Can it be read back from the terminal?

Not cleanly. PgTerminal (client-v2/src/utils/terminal/terminal.ts) exposes only write-side helpers — println, clear, enable, focus, process, run, colour helpers — plus a get(). There is no scrollback-reading API, and what is in the buffer is post-improveOutput and ANSI-encoded anyway.

Options for the bridge

  • Preferred: capture at the source in build.ts by adding the raw stderr to a state module. Small change, but see the merge-risk note — build/build.ts is a file upstream actively edits.
  • Alternative: have the assistant call PgServer.build itself for its own context. Costs a second compile and diverges from what the user saw.
  • Alternative: subscribe to PgCommand.build.onDidFinish (the mechanism exists — program-info.ts uses PgCommand.deploy.onDidFinish) and read whatever state is exposed. Only works once the raw text is exposed.

Verdict. Needs a deliberate decision before task-01. This is the one piece of required context the client does not currently keep.

Program id and deploy state

Program id

PgProgramInfo holds kp (a generated Keypair), customPk (a user-supplied override) and a derived pk/getPkStr(). build.ts generates a keypair on first build if none exists and rewrites the declare_id! macro in the sources before sending them.

PgProgramInfo.uuid — the server's session id, required by GET /deploy/{uuid}.

Last build failed

PgProgramInfo.lastBuildFailed (boolean)

Deploy state

PgGlobal.deployState, a union of "ready" | "loading" | "paused" | "cancelled" (client-v2/src/utils/global.ts). PgGlobal.buildLoading covers builds. Deploy progress is pushed to the UI via PgView.setMainSecondaryProgress(n).

Build flow

  1. PgCommand.build.execute() — from the Build button (views/sidebar/build-deploy/) or the build terminal command.
  2. client-v2/src/commands/build/build.ts sets PgGlobal.buildLoading = true and prints 'Building...'.
  3. getBuildFiles() walks PgExplorer.files, keeps only paths under PgExplorer.getCurrentSrcPath().
  4. If no program keypair exists it generates one (PgWeb3.Keypair.generate()) and stores it on PgProgramInfo.
  5. It rewrites declare_id!("...") in the first Rust file that has one — lib.rs and id.rs are checked first — skipping line and block comments. Python projects get the equivalent declare_id(...) rewrite.
  6. If any .py files are present, seahorse-compile (WASM) transpiles them to Rust first; otherwise the Rust files go straight through.
  7. PgServer.build({files, uuid, flags}) POSTs to ${PgSettings.server.endpoint}/build (client-v2/src/utils/server.ts).
  8. The server compiles and responds {stderr, uuid, idl}.
  9. build.ts derives failed from stderr.includes('error: could not compile') and calls PgProgramInfo.update({idl, uuid, lastBuildFailed: failed}).
  10. improveOutput(result.stderr) is printed to the terminal. The raw stderr is discarded here.
  11. finally: PgGlobal.buildLoading = false.

Deploy flow

  1. PgCommand.deploy.execute(); preChecks are checkWallet and checkProgram.
  2. checkProgram triggers a build first if there is neither a uuid nor an imported program, and warns if lastBuildFailed is set, because the server retains the previous binary and would otherwise silently return a stale one.
  3. A state machine on PgGlobal.deployState guards re-entry: ready -> loading; a second invocation while loading sets paused; cancelled throws.
  4. PgView.setMainSecondaryProgress(0.1) starts the progress bar over the terminal panel.
  5. processDeploy() runs. It fetches the ELF with PgServer.deploy(uuid) — GET /deploy/{uuid}, returned as a Uint8Array — then writes and deploys it through client-v2/src/commands/deploy/bpf-loader-upgradeable.ts, signing with PgWallet against PgConnection.current.
  6. On success the elapsed time is printed; finally the progress bar resets and deployState returns to ready.
  7. NOTE: the transaction-level detail inside processDeploy was not read line by line — see unknowns.

Share flow

  1. The explorer's share action POSTs the project to /new via PgServer.shareNew({explorer: {files: {path: {content}}}}).
  2. The server stores it in MongoDB and returns a share id as plain text.
  3. Opening /share/:id routes through client-v2/src/routes/share/, which GETs /share/{id} and loads the returned files into a temporary workspace (PgExplorer.isTemporary).
  4. NOTE: in production builds both share calls are forced to https://api.solpg.io by the useDbServer flag in utils/server.ts, ignoring the configured endpoint.

WASM boundary

  1. All WASM is loaded lazily. client-v2/src/utils/package.ts is the single gateway: PgPackage.import(name) switches over a dynamic import() per package and wraps failures in a 'Failed to load X' error surfaced to the terminal.
  2. Terminal CLIs: solana -> runSolana, anchor -> runAnchor, spl-token -> runSplToken, sugar -> runSugar, each called with the raw input string from commands/<name>/<name>.ts.
  3. Seahorse: compileSeahorse(content, programName) returns a FLAT array alternating [path, content, path, content, ...]; build.ts also patches '# [program]' back to '#[program]' because the output is not rustfmt-ed.
  4. rustfmt: imported by components/Editor/Monaco/Monaco.tsx for formatting.
  5. rust-analyzer: the exception to the lazy pattern — it runs in a Web Worker (languages/rust/rust-analyzer/worker.ts) using --target web plus wasm-bindgen-rayon threads. The main thread talks to it through a Proxy where every property access becomes an async postMessage round trip. Note initRustAnalyzer wraps worker creation in PgCommon.tryUntilSuccess(createWorker, 10000), which retries forever if the worker fails to signal readiness.
  6. playnet: utils/playnet/ wraps the WASM Playnet runtime and overrides the web3.js Connection when the cluster is playnet.

09Conventions

Code style

Source

CONTRIBUTING.md

Typescript

  • 80 character limit, 2-space indent, enforced in CI via prettier
  • Avoid any and // @ts-ignore
  • Do not import @solana/web3.js directly — use PgWeb3
  • Avoid importing Anchor packages directly (an active effort to reduce dependence)
  • Import order: react, external, internal, with a blank line between external and internal
  • Prefer import type for types
  • Default exports for React components, named exports for everything else
  • Prefer lazy loading for big imports
  • Prefer functional programming over OOP; no inheritance
  • Prefer const f = () => {} over function f() {}
  • At most one optional parameter; bundle the rest into a single opts?: {...} object
  • No non-ASCII characters in source code (fine in Markdown)
  • Prefer inlining a function used only once
  • Order functions by importance and call order — main function at the top
  • Prefer no new dependency when feasible
Rust

rustfmt with group_imports = StdExternalCrate, imports_granularity = Crate, style_edition 2021 (server/rustfmt.toml)

File naming

kebab-case for module folders and non-component files; PascalCase.tsx for React components. Sidebar page folders must be the kebab-case of the page name, because createSidebarPage derives the import path from it.

Commits and PRs

  • Present tense ("Add feature", not "added feature")
  • Prefix with the change location for non-client changes ("server: Add feature"); client changes take NO prefix
  • Prefer small PRs; open an issue first for large ones
  • Test locally before opening a PR; tests are not required
  • If using an LLM, understand the changes being made

Project specific

  • Branch for this work: feat/client-2-ai-assistant (per CLAUDE.md)
  • The mock boundary must be a single clearly named module, swappable for the real implementation

11Unknowns

These are open questions, not findings. Nothing here has been verified.

What does "client-2" mean concretely?

Why it matters

CLAUDE.md says new work goes into a second client developed in parallel and that the existing client/ should not be modified beyond what is strictly necessary. task-01 says to add a dockable panel next to the editor and to reuse the existing layout. Those describe different codebases. It decides where every file lands and whether the sidebar-registry seam is available at all.

How to resolve

A decision from the team. Not answerable by reading the repo.

How should the raw build stderr reach the assistant?

Why it matters

It is required by task-01's getProjectContext and is the one piece of context the client does not retain. Every available route has a cost: editing a hot file, recompiling, or accepting the lossy improveOutput text.

How to resolve

A design decision for task-01. The mechanics are now fully known — see project_context_available_in_client.build_errors.options_for_the_bridge.

What exactly happens inside processDeploy?

Why it matters

The demo's final step is deploy-to-devnet with an Explorer link. Failure modes there (airdrop needed, program size, upgrade authority) shape what the assistant should say when it goes wrong.

How to resolve

Read client-v2/src/commands/deploy/deploy.ts past line 70 together with bpf-loader-upgradeable.ts. Roughly an hour.

How complete is the existing wallet-standard support?

Why it matters

Focus 2 of the product brief is real wallet adapters. WalletState already carries standardWallets and standardName, so some of it may exist. Scope of that focus area depends on the answer.

How to resolve

Read client-v2/src/utils/wallet/ in full and check which @solana/wallet-adapter packages are actually wired up. Not needed for task-01.

Where should an assistant's own persisted state live?

Why it matters

Conversation history, and a user-supplied API key, need somewhere to go. There are three existing precedents — local storage (wallet), the virtual filesystem (program-info), and the settings registry — and picking wrong means either leaking a key into a shared project or losing history on workspace switch.

How to resolve

A design decision for task-01, informed by the fact that PgExplorer state is per-workspace and is what gets serialised into a share link.

Is there a client-side cap on build request size?

Why it matters

PG_PAYLOAD_LIMIT defaults to 1048576 bytes server-side. If the assistant ever sends generated files, hitting it would surface as an opaque failure.

How to resolve

Check whether the client validates size before POSTing; the server rejects above the limit.
