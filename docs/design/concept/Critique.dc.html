ITERATION 3 — CONCEPT
Why re-plan the layout, not just repaint it
The brief positions Playground as the top of the official onboarding funnel — a newcomer's first contact with Solana development, before any local setup. The current anatomy is a small VS Code: it assumes you already know what an IDE is for. The concept flips the frame: the UI should teach the loop it executes.
1 · NAVIGATION IS A TOOL TAXONOMY
The rail lists Explorer / Build / Test / Tutorials / Programs — categories for someone who already thinks in IDE panels. The newcomer's question is never "where is the Build tab", it is "what do I do next?"
2 · PRIMARY ACTIONS ARE BURIED
Build and Deploy — the two most important buttons in the product — are micro-buttons inside an explorer section header, or terminal commands.
3 · FEEDBACK = RAW COMPILER OUTPUT
The terminal is the primary feedback channel — the scariest possible surface for the target user. The assistant softens it, but the layout still routes every outcome through stderr.
4 · NO STATUS MODEL
Built or not, deployed where, which cluster, how much SOL — none of it is visible. The wallet is a tiny "Not connected" in the status bar.
5 · THE ASSISTANT IS ONE TAB AMONG SIX
The brief's Focus 1 — the differentiator of the whole product — competes for the same sidebar slot as the file tree. A co-pilot that disappears when you open a file is not a co-pilot.
THE FRAME OF THE CONCEPT — THE USER'S ACTUAL LOOP
Write
editor + templates
→
Build
errors explained, fixes applied
→
Deploy
devnet + Explorer link
→
Interact
IDL panel, transactions
Every capability the environment already has — server build, devnet deploy, the IDL-generated test panel — maps onto exactly one stage of this loop. Direction B makes the loop itself the navigation; the assistant rides alongside the whole way.
